# Semantic spec-compliance audit — NUT-04 (mint quotes) & NUT-20 (locked mint quotes)

greatspectations Layer 2 audit of pecan's mint-side implementation (wallet
custom-method handler + processor gRPC backend) against the Cashu NUT specs.

- Spec sources: `/Users/macbook/src/nuts/04.md` (NUT-04), `/Users/macbook/src/nuts/20.md` (NUT-20)
- Implementation sources (read in full):
  - `web/src/lib/coco/mint-branch-handler.ts` (wallet: quote creation, NUT-20 key handling, execute/recover)
  - `web/src/lib/coco/coco-wallet.ts` (wallet flows: `createDepositQuote`, `pollAndMint`, `getPendingDeposits`)
  - `processor/src/backend.rs` (processor: `MintPayment` impl — quote creation, settle eventing)
  - `web/src/lib/coco/branch-methods.ts` (method type declarations)
- Corroborating reads (cited where used, read to avoid speculation):
  `processor/src/state.rs` (ticket ids, `mark_paid`), `processor/src/web.rs` (`verify_with_mint` settle
  cross-check), `processor/src/ln.rs` (invoice description).
- Architecture fact that shapes many verdicts: pecan's processor implements cdk's
  `MintPayment` gRPC trait. **Blind-signature issuance (POST `/v1/mint/{method}`), NUT-20 signature
  verification at mint time, quote-id generation, and the `amount_paid`/`amount_issued`/`updated_at`
  accounting live inside cdk-mintd** — the gRPC surface pecan implements carries no mint-tokens call
  (`backend.rs:300-630` implements settings/quote/wait/check only). Requirements enforced purely at
  that layer are graded ➖ with justification, while pecan's *compensating* enforcement at the
  processor layer is cited where it exists.
- Audited rails: `branch`/`ln`/`btc` on the EUR/USD pairs. The external sat mint (signut, bolt11) is
  out of scope. NUT-05/08 (melts) are covered by a parallel audit and excluded here.

## Findings

### F1 — ⚠️ P2 (hygiene, compensated): branch-rail payment request is the quote id

`request: ticket.id` with `id: format!("MINT-{quote_id}")`
(`processor/src/backend.rs:406`, `processor/src/state.rs:118`) — the NUT-04 clause
"`quote` … **MUST NOT** be derivable from the payment request" (04.md:89) is literally
violated for the `branch` rail, and the wallet further shows the quote tail to the teller
(`coco-wallet.ts:336`).

Why this is P2 and not P0: the clause exists to stop *front-running theft* by parties who
intercept the payment request. That threat is closed by the deployment's mandatory NUT-20
locks (NUT20-R6): a quote-id eavesdropper still cannot mint — spec error 20008 at the mint —
and the spec's own CAUTION text prescribes exactly this remedy ("To prevent this, use NUT-20
locks"). The design is also unavoidable for a counter rail: there is no external payment
instrument; the teller code *is* the payment. Risk that remains is social (a rogue teller
settling a ticket without cash), which lock-enforcement does not address and which is an
operator-trust question outside spec scope.

Suggested fix: none required for correctness. Optional hardening: have
`docs/wallet-integration.md` state explicitly that the branch `request` embeds the quote id
and that safety rests on the mandatory lock (it already documents the lock requirement), so
third-party wallet authors don't treat `request` as a secret-bearing instrument on this rail.

### F2 — ⚠️ P2 (interop): btc-rail minimum enforced but not advertised

The processor rejects onchain deposits below `MIN_ONCHAIN_ORE = 5_000` cents
(`backend.rs:45,260-266`) but advertises empty settings — `custom.insert("btc", "{}")`
(`backend.rs:321-323`) — so the NUT-06 `MintMethodSetting.min_amount` that 04.md:179-185
provides for exactly this purpose stays unpopulated. Generic wallets must discover the €50
minimum by trial-and-error against the error string.

Suggested fix: populate the per-method settings JSON string in `get_settings` with
`min_amount` (5_000) for `btc` (and any per-method `options`), after verifying the exact
schema cdk-mintd expects for custom-method settings in the vendored cdk version; keep the
creation-time check as the enforcing layer.

### F3 — ⚠️ P2 (interop): unlocked-quote refusal may not surface as NUT-20 error code 20009

When a third-party wallet creates an unlocked quote, the processor answers
`Error::Custom("branch mint quotes must be locked to a wallet key (NUT-20): …")`
(`backend.rs:380-386`; same for ln `:220-226`, btc `:268-274`). The spec's error table
defines `20009` "Mint quote requires `pubkey` but none given or invalid `pubkey`"
(20.md:204) for precisely this case. Pecan's code cannot prove which HTTP code cdk's gRPC
error mapping produces for a processor `Error::Custom` — if it is not 20009, generic wallets
get an opaque 4xx/5xx instead of the spec-defined signal. Pecan's own wallet is unaffected
(it always locks, `coco-wallet.ts:300,308`).

Suggested fix: verify the mapping once (e.g. add a case to `scripts/api-smoke.sh` that
creates an unlocked quote and asserts the surfaced code), and if cdk permits propagating a
code, return the typed error that maps to 20009; otherwise document the observed wire error
in `docs/wallet-integration.md`.

**Bottom line:** the mint-quote path is spec-solid where pecan owns it. The two deliberate
deviations — request-embeds-quote-id on the branch rail and mandatory NUT-20 locks — are
 mutually compensating and follow the spec's own CAUTION guidance; the genuine gaps are
 advertisement/error-surface polish (F2, F3), not money-safety. The strongest property
 verified: a third party who learns a quote id cannot mint on this deployment, because
 unlocked quotes cannot exist through this processor (creation-time refusal, re-checked at
 settle) and issuance itself is signature-gated inside cdk-mintd.
