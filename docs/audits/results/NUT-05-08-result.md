## Findings

### F1 (⚠️ P1, interop) — `FAILED` quote state is emitted out-of-spec and mishandled on both sides

- **Spec**: NUT-05 L82-86 defines exactly `"UNPAID" | "PENDING" | "PAID"`.
- **Processor**: `backend.rs:540-544` maps `TicketStatus::Failed` →
  `MeltQuoteState::Failed`, reachable when a teller voids a ticket
  (`mark_failed`, state.rs:530; `/api/tickets/{id}/mark-failed`, web.rs:112).
- **Wallet, melt POST path**: `melt-branch-handler.ts:92-93` coerces every
  state that is not `PAID`/`PENDING` — including `FAILED` and `undefined` —
  to `"UNPAID"`, and coco then restores the input proofs to spendable
  (coco-core dist:8359-8360). If the mint burned the inputs before the
  failure surfaced, the wallet shows money that no longer exists.
- **Wallet, state-check path**: coco's `checkPending` throws
  `Unexpected melt quote state: FAILED` (coco-core dist:8484-8489) and
  `pollWithdraw` swallows all refresh errors (coco-wallet.ts:668-676), so a
  voided-after-fund-lock withdraw stays "pending" in the UI until the
  45-minute staleness cutoff hides it (coco-wallet.ts:922-928) — while the
  proofs stay burned. The customer has no in-wallet signal that the payout
  was refused.
- **Severity**: P1. No mint-loss path (the mint's own ledger is the
  authority and rejects double-spends), but it is a real interop break on
  the one state that matters in the dispute flow, with a phantom-balance
  variant.
- **Fix**: in `MeltBranchHandler`, classify `"FAILED"` explicitly (fail the
  operation, surface a terminal error to the UI) instead of the
  unknown→`UNPAID` coercion; reserve the coercion strictly for a missing
  `state` field, and treat that as an error too unless the response shape
  is known to omit it. Processor-side, consider whether voiding a
  fund-locked (pending) outgoing ticket should instead require an explicit
  operator refund flow rather than a bare `FAILED`.

### F2 (⚠️ P1, recovery/robustness) — change recovery depends on an unspecified mint extension, and the docs contradict the code about it

- **Spec**: NUT-05 L96 — the quote-check response has "the same structure
  as the initial quote response", whose schema (L57-71) has no `change`
  field. NUT-08 delivers `change` only in the melt POST response
  ("together with the successful payment status", L41).
- **Pecan**: `MeltBranchHandler.checkMeltQuote`
  (melt-branch-handler.ts:107-123) reads `q.change` from the quote check to
  recover an overpay when the melt response was lost — the only NUT-08
  recovery path for branch melts.
- **Contradiction**: the handler comment (melt-branch-handler.ts:29-31)
  claims "the mint (cdk-mintd ≥ 0.18.0) re-serves change signatures on
  quote checks", while docs/lightning-mint.md:236-238 (§Melt saga
  constraint 3) records that cdk-mintd 0.18.0-rc.0's custom-method check
  response "has no `change` field at all" and only master re-serves it
  ("re-check when upgrading"). Both cannot be true for the deployed rc.0.
- **Severity**: P1, not P0, only because the exact-amount pre-swap
  (NUT08-R9) makes the common case change-free; the residual exposure is
  the "swap cannot be exact" corner the handler comment itself names, plus
  any future rail with a nonzero `fee_reserve`.
- **Fix**: (1) verify against the actually-deployed cdk-mintd build whether
  custom-method quote checks carry `change`, and update whichever of the
  two comments is wrong; (2) persist that verification as an e2e assertion
  (the suite already asserts "zero change on finalized teller melts" —
  add a reload-during-melt case that deliberately overpays and asserts the
  change re-serve, so a mint upgrade that drops the extension fails CI);
  (3) if the extension is absent, make the no-blank-outputs invariant a
  hard precondition (refuse melts that would carry change) rather than a
  best-effort policy.

### F3 (⚠️ P2, hygiene) — sat-melt race accepts `rolled_back` as benign alongside `finalized`

- `createSatMeltWithdraw` (coco-wallet.ts:601-618) treats the mint's
  "inputs already spent" error as benign when the op row reaches
  `finalized` **or** `rolled_back` within 10s.
- The `finalized` half is spec-sound: the mint guarantees a single
  successful melt per quote, the change went to the winner's blank
  outputs, and the winner is the same wallet writing the same op row.
- The `rolled_back` half is not: rolled-back means the proofs were restored
  to spendable locally, while the triggering error says the mint burned
  them. That combination (reachable only if the losing driver's own error
  path rolls the op back while the winner is mid-write, or on a genuine
  desync) leaves a phantom balance that will fail loudly — with the very
  same "already spent" error — on the next spend of those proofs. No mint
  loss, but a confusing wallet state and a withdraw the UI may report as
  failed while the invoice was paid.
- **Fix**: accept only `finalized` as benign. On `rolled_back` (or on the
  10s timeout), force a quote-state check / NUT-09 restore for the quote
  before deciding, so the op converges to the mint's truth instead of the
  loser's local write.

Row count is by primary verdict; NUT05-R11 counts once as ✅ (wallet
tolerates both shapes) — its mint-side observation (cdk signaling pending
via error 20005 instead of 200-OK-PENDING) is a cdk-mintd deviation noted
in-row, not a pecan verdict.

Overall: the melt pipeline is spec-shaped where the spec speaks — quote
request/execute payloads, `prefer_async` flow, state polling, fee_reserve
= 0 accounting, NUT-08 blank-output mechanics in the libraries pecan
rides — and its one deliberate divergence (exact-amount pre-swap instead
of overpay-and-recoup) is a documented, spec-permitted hardening. The
open risks cluster exactly where the spec is silent and cdk fills the gap
with its own semantics: the fourth `FAILED` state (F1) and change
re-serving on quote checks (F2).
